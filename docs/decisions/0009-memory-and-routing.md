# 0009 记忆与自动路由的分层、存储和统计口径

**日期：** 2026-11-05 **状态：** 已接受，已接入 `memory/`、`routing/`（GLO-20、GLO-23、GLO-24、GLO-31）

**背景：** 自动路由要在取词和 Action 之间选出功能，并从用户的改正里学习。需要决定代码放在哪层、记录存什么、准确率怎么算。

**决定：**

**分层。** `memory/` 和 `routing/` 是两个只依赖标准库和 `core` 的包，不认识界面、取词和服务（`arch_test.go` 检查）。路由只做选择，不启动 Engine、不碰剪贴板、不写回，这些都由 `app/` 做。

**存储。** 一行一条 JSON，写在 `<配置目录>/memory/usage.jsonl`，权限 0600。每次取词（会话）一条，**不存选中文本和结果**，只存形状（字数、行数、文字类别、结构标记等）、来源应用 bundle id、是否可编辑、候选、初始选择及来源、规则分数、改正序列、最终功能、结果、是否复制或替换、各阶段耗时。默认保留 90 天、最多 5000 条，超出时压缩重写。可在托盘关闭和清空。运行中的 Gloss 和 `gloss` 命令共用这个文件：追加、标注、清空和压缩都持有旁边 `usage.jsonl.lock` 的文件锁（`flock`，Windows 上暂为空操作）；压缩只以锁内重读的磁盘内容为准，不用进程里可能过期的快照，所以另一方的新增、标注和清空都不会被覆盖或复活；`stats`、`recent` 只读，不裁剪也不重写；`label` 追加一行新记录，同一会话的后一行取代前一行。

**路由顺序。** 规则 → Jev（规则不确定且配置了 Jev 时，有界等待，默认 800ms）→ 记忆偏好（相同应用且相似文本，其次相同应用）→ 最近一次明确选择 → 默认功能（启用列表第一个）。规则只有在某功能得分 ≥0.7 且领先第二名 ≥0.25 时才算判定；任何单一信号都达不到阈值。

**偏好。** 用户切换功能（改正）或手动选择是强证据（权重 1）；自动选出、用户又复制或替换了结果的算弱证据（0.3）；只是看了不算证据，避免路由不断强化自己。半衰期 21 天。少于 3 次明确选择标为“证据不足”，前两名差距小于 0.2 标为“偏好不一致”，两种情况都不用于决定。

**统计口径**（`gloss stats`）：

| 指标 | 定义 |
|---|---|
| 改正率 | 有改正的会话 ÷ 自动路由的会话。改正不等于全部错误 |
| 已确认准确率 | 标注为对的 ÷（标注过的 + 未标注但改正过的）。只有 `gloss label` 能把会话标为对 |
| 未知比例 | 既没改正也没标注的会话 ÷ 自动路由的会话。它们**不算对** |
| 回退率 | 由“最近选择”或“默认功能”决定的比例 |
| 路由耗时、改正后额外等待 | p50 和 p95 |

**理由：** 可解释的加权统计足够冷启动，也便于实测时说清每次为什么这样选。不存文本，记忆泄漏的风险就小得多。JSONL 追加写入简单。实测（macOS，2026-11-05，临时测试）：连续写 5200 条，平均每条 34µs，含压缩重写的最慢一条 1.5ms；在约 5000 条记录上提炼一次偏好 1.4ms。

**代价：**

- 规则阈值和权重是在开发者自己写的 35 条样例上调出来的，有过拟合风险，实测数据才算数。
- “最近一次明确选择”是全局的：一次手动选择会影响之后所有规则判断不了的情况，包括别的场景（本地已观察到，见 STATUS）。是否收窄到同一应用，等实测数据再定。
- 不存文本，以后若要做“个人术语表”之类功能，需要新的决策。
