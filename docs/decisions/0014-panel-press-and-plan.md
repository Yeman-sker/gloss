# 0014 面板不猜手势，打开前先定框架

**日期：** 2026-11-06 **状态：** 已接受，已接入 `app/`（GLO-22），等负责人上手确认

**背景：** 负责人实测（GLO-22）：按下面板时靠距离和时间猜用户是要复制、选中还是拖动，经常猜错，想选中时变成了复制。长文流式时面板不停地改高度、改宽度，还上下抖。数据见[实测](../research/2026-11-06-panel-streaming.md)。

**决定：**

1. **按下去的地方决定做什么，不再判断手势。** 按在文字上是选中，按在其他地方是拖动，复制只走右下角的按钮。点击面板不再复制。
2. **打开前先定框架。** 结果开始到达后，等到结束、满 64 字或满 180ms，再根据原文、结果类型和已到的内容定下宽度和大致高度（`app/plan.go`）。此前胶囊继续等待。宽度定下后这次运行不再变。
3. **窗口只为计划移动。** 靠近屏幕底部时，打开时一次上移够计划的空间。文字超出计划时，窗口按 120pt 一步上移，直到有一页可读；之后不再上移，文字在面板里滚动。
4. **文字由 `app/` 的节奏器放出**（`app/pace.go`），Markdown 按块放出，不再直接按网络到达的节奏显示。
5. **不缩放写满文字的面板。** 关闭、拖动、让路都不用整体缩放，只有胶囊打开时还有。拖动的“抬起”改用阴影。

**理由：** 手势判断错了的代价很高，而且用户没有办法纠正；按位置分配是可预期的。框架先定下来，文字才不用重排，跟随滚动才有一个不变的目标。多等最多 180ms 换来打开时就接近最终大小，这段时间胶囊本来就在等待。缩放的开销是实测的，每帧多 20–40ms。

**代价：**

- 点击复制这个快捷操作没有了，要多移动一次鼠标到按钮。
- 结果开始显示最多晚 180ms。
- 预估会错：结束时可能收回或长高一段。
- 靠近底部时，阅读布局的面板离选区更远；结果很短时这段距离是白移的。
- 流式期间窗口更大，内存多约 6 MB。
- 拖动时没有了放大的手感，只有阴影变化，观感待负责人确认。
