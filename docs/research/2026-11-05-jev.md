## Jev 是什么（据官方文档，未实测）

| 项目 | 内容 |
|---|---|
| 提供方 | TypeSafe。云端 API，没有本地部署，所以没有体积和内存问题，但每次判断都要联网 |
| 接口 | `POST https://api.typesafe.ai/v1/systemone`，`Authorization: Bearer <key>` |
| 请求 | `state`（一段描述当前情况的文本）、`model`、`questions`。每个问题 `type: "choice"`，带 `instructions` 和 `criteria`（选项 → 描述） |
| 返回 | `answers.<问题>.choice`、`confidence`、`probabilities`（每个选项一个分数） |
| 模型 | `jev-latest`，文档写明当前指向 `jev-1.14.0` |
| 限制 | 每次请求最多 64k token，单个问题 32k；选项最多 255 个 |
| 费用 | 输入每百万 token 0.042 美元。一次路由约 0.5–1k token，粗算每千次几美分（推测） |
| 数据 | 文档称不用客户请求训练；零数据保留只对企业版 |
| 延迟 | 文档没有给出数字 |
| 分数含义 | 文档没有说明 `confidence` 是否经过校准。**不能当成“猜对的概率”**，阈值（默认 0.6）只能等实测数据校准 |

## Gloss 发给 Jev 的内容

见 `routing/jev.go` 的 `State`，单测覆盖：

- 选中文本，超过 1200 字只发开头和结尾各 600 字。
- 来源应用的 bundle id、是否可编辑、文本形状（字数、行数、文字类别、是否有 Markdown 结构）、用户语言。
- 偏好摘要（各情境下功能的占比、样本数、证据不足或不一致的标记、最近的明确选择和改正），由 `memory.Snapshot.Summary` 生成。
- **不发**：Key、窗口标题（除非 `routing.send_window_title` 为 true）、选中文本前后的上下文、历史文本（记忆本来就不存文本）。
- 候选功能的 `criteria` 用各功能的 `Name：Purpose`，只包含已启用的功能；Jev 返回不在候选里的功能时丢弃。

## 规则样例粗测（已实测，macOS，2026-11-05）

样例在 `routing/testdata/samples.json`，35 条：翻译 10（3 条歧义）、释义 9、提示词 8（2 条歧义）、Agent 输出 8（1 条歧义，1 条期望翻译：在 Claude 里选中的英文句子）。`go test ./routing -run TestSamples -v` 打印逐条结果。

| | 结果 |
|---|---|
| 明确样例 29 条 | 规则判对 29、判错 0、未判定 0 |
| 歧义样例 6 条 | t8–t10（只读环境里的英文词句）被判为翻译；p7、p8、a8 没判定，走默认 |
| 耗时 | 最慢约 11µs |

已知偏差：

- 只读环境里的英文单词，规则一律判翻译。用户其实可能想看释义，这正是该交给 Jev 或记忆的情况，但现在的阈值让规则先判了。实测时要看改正率。
- 可编辑的英文句子（如在 TextEdit 里）规则得分 0.65，不够阈值，会落到记忆。本地运行时观察到：前一次手动选了“优化提示词”，之后这类句子都按“最近选择”走了提示词（见 STATUS）。

## 测 Jev 的方法

1. 在配置文件 `services` 里加一个服务，例如 `"jev": {"base_url": "https://api.typesafe.ai/v1", "api_key": "...", "model": "jev-latest"}`，并设 `routing.jev_service` 为 `"jev"`。
2. `go run ./cmd/routebench -n 3`：每条样例问 3 次，打印规则和 Jev 各自的选择、Jev 的把握，以及 Jev 延迟的 p50、p95 和最大值。不打印 Key。
3. 把结果补到本文，注明网络环境。若 p95 超过 800ms，调高 `routing.wait_ms` 或只在样例显示 Jev 明显更准时启用。
