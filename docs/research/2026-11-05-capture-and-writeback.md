# 取词、剪贴板与写回的实测（GLO-8、GLO-9、GLO-11、GLO-14、GLO-28）

**日期：** 2026-11-05 **平台：** macOS（Apple Silicon，Darwin 27） **作者：** Claude Code

测试都在我自己新建的 TextEdit 文档里进行，没有向用户已打开的窗口发送按键。测剪贴板前先备份，测完核对与备份一致。

## helper 协议与可靠性（GLO-28）

- 请求和响应带 `id`。Go 客户端为每个请求设超时（取词 2s，替换 3s），超时、退出或返回无法解析的内容时杀掉并重启 helper；迟到的、`id` 不匹配的响应直接丢弃。单测用假 helper 覆盖了这几种情况（`capture/capture_test.go`）。
- 错误分类：`permission`、`no_selection`、`timeout`、`exited`、`protocol`，面板各自给出不同提示。
- Rust 侧所有 Create/Copy 得到的 CF 引用由 RAII 包装释放。

| 内存（实测） | 结果 |
|---|---|
| 旧 helper，2000 次取词 | 2.6MB → 3.1MB，持续上涨 |
| 新 helper，600 次和 2000 次 | 稳定在约 4.3MB footprint（链接 AppKit 后基线高约 1MB） |

## 来源信号（GLO-11）

| 信号 | 结果（TextEdit 实测） |
|---|---|
| 来源应用 | bundle id，`com.apple.TextEdit`。前台应用改用 AX 的 `AXFocusedApplication`，取不到时用窗口列表，不再启动 `lsappinfo` |
| 窗口标题 | 能取到。默认只给路由，不发给模型 |
| 是否可编辑 | 三态，`AXValue` 或 `AXSelectedText` 可写为 yes。取不到为 unknown |
| 前后文 | 用 `AXStringForRange` 取选区前后各 300 个 UTF-16 单元；失败时只在全文不超过 20000 字时读 `AXValue` 截取。前后文只填进 `Request.Context.Surrounding` |
| 耗时 | 新进程第一次约 72–111ms（加载 AppKit），之后 0.2–5ms。旧 helper 每次 6–8ms，主要花在启动 `lsappinfo` 查询前台应用上 |

未测：浏览器、终端、备忘录、Electron 应用里各信号能否取到。Chromium 内核的浏览器后来测了，见 [Arc 排查](2026-11-06-arc-capture.md)。

## 剪贴板恢复（GLO-8）

Cmd+C 兜底前保存剪贴板的全部 item 和全部类型，复制后读取，再按原样写回。恢复前检查 `changeCount`：如果在这期间剪贴板被别人改过（用户自己复制了新内容），就不恢复，不用旧快照覆盖新内容。

| 剪贴板原内容（实测） | 恢复后 |
|---|---|
| 图片（public.tiff） | 类型和数据完全一致 |
| Finder 复制的文件（file URL） | 一致 |
| 纯文本（含 Raycast 附加的私有类型） | 一致 |
| 富文本 | 原有类型一致，系统额外派生出 `public.utf16-external-plain-text` |

兜底路径耗时：55–65ms。修复前 Cmd 键会被卡在按下状态（见下），兜底要约 578ms。

**发现的 bug（已修）：** 旧 helper 和最初的新实现发 Cmd+C 时，按键抬起事件仍带着 Cmd 标志，结果系统认为 Cmd 一直按着（实测 HID 标志 `0x20100000`）。这会让下一次取词等待按键松开 400ms，也可能影响用户接下来的输入。现在按“Cmd 按下、C 按下、C 抬起、Cmd 抬起”完整发送，标志恢复为 `0x20000000`。这可能与 GLO-9 有关，未证实。

## 写回（GLO-14、GLO-29）

取词时 helper 保存一个目标凭证（token，最多 8 个）：进程、焦点元素、选中文本和范围、是否可编辑。替换时先等用户松开按键，再依次检查：有辅助功能权限、目标可编辑、前台仍是同一进程、焦点元素相同（`CFEqual`）、选中文本和范围都没变；任何一项不符就拒绝，并说明原因。粘贴前再核对一次前台和焦点。

写入方法默认是 `auto`：字段声明 `AXSelectedText` 可写时先用 AX 直接写。之后不看 AX 的返回码，只看字段：新文字在原位置、且选区已不是读取时的那一段，算确认落地；选区变了但看不到新文字，算“已写未确认”，不再粘贴；选区原样（AX 什么都没写）才改用粘贴。“选区已变”这一条防止结果恰好是原文开头时（`hello` 替换 `hello world`）误判为成功。粘贴前的最后检查同时核对前台、焦点和选区。按键（粘贴的 Cmd+V、兜底取词的 Cmd+C）用 `CGEventPostToPid` 只发给目标进程，不再发给全局。

| 方法 | TextEdit（实测，macOS） |
|---|---|
| auto（默认，走 AX） | 写入正确，回读校验通过，剪贴板不动 |
| 粘贴（发给目标进程） | 写入正确，回读校验通过，剪贴板恢复原样 |
| AX 直接设置 | 写入正确，可撤销 |
| Cmd+C 兜底（发给目标进程） | 取到文字，剪贴板恢复原样 |
| 选区移动后替换 | 拒绝（changed） |
| 原文被改后替换 | 拒绝（changed） |
| 取词后切到另一个应用再替换 | 拒绝（changed），原文不变 |
| 结果是原文开头（`hello` 替换 `hello world`），auto 和粘贴 | 都写入正确并确认 |

在面板里点“替换”的端到端测试（2026-11-05，模拟模型服务，TextEdit）：

- 第一次被误拒为“另一个应用在前台”：点 Gloss 的面板会让 AX 把 Gloss 当成焦点应用。已修，判断前台时跳过 Gloss 自己。
- 修复后再测，粘贴没有落到 TextEdit，第二次换了正常条件仍然一样。原因是点击面板会让它成为键盘窗口（Gloss 不激活），全局发出的 Cmd+V 进了面板。此前把它归因于当时的系统权限弹窗，是错的。同理，面板是键盘窗口时，全局 Cmd+C 也会发给面板。改为 AX 优先、按键只发给目标进程后，面板里的替换实测成功：AX 写入，回读确认，剪贴板未变，面板随后自动关闭。
- 未确认时的提示（边际审查发现，已修）：helper 报告 `verified:false` 时，面板过去仍显示“已替换”并关闭；`unverifiable`（没能读到原选区，**没有写入**）反而被当成“已写入未确认”。现在三种情况分开：没写入说明原因；写了但没确认提示“已写入，但没能确认结果，请检查原文”并保留面板，不再提供替换，避免重复写入；确认后才显示“已替换”。helper 超时或退出时请求可能已经生效，按“结果未知”处理，同样不再提供替换。

未测（需要负责人的常用应用）：ChatGPT 网页、Claude 桌面端输入框、备忘录、终端。这些应用是否支持 AX 设置、AX 写入能否撤销、是否处理发给进程的按键，都要在实测里补进上表。AX 写入在部分应用里可能不进撤销栈（推测，未测）。

## Claude 桌面端多段选择（GLO-9）

本机没有复现条件（不能向负责人的 Claude 窗口发送按键），未复现。已做的改动：

- 对每个进程设置一次 `AXManualAccessibility`（Electron 应用要靠它打开辅助功能树），取不到时 80ms 后重试一次。
- AX 调用超时设为 0.8s，避免卡住。
- 修复了上面 Cmd 键卡住的问题。
- 兜底的 Cmd+C 改为只发给前台应用的进程：面板曾被点过、成为键盘窗口时，全局 Cmd+C 会进面板，取词就会失败。这是一个可能的原因，未证实。
- 两条路都失败时，日志里分别写明 AX 和兜底各自的失败原因（`capture: ... copy produced nothing` 等），方便实测时判断是哪一步出错。

验收（连续多次选中多段文字都能取到）需要负责人在 Claude 桌面端实测。
