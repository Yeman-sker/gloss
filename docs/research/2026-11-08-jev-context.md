# 只用 Jev 判断：丰富上下文的第一次对比

**日期：** 2026-11-08 **平台：** macOS（Apple M4，macOS 27），经本机 127.0.0.1:3425 的本地网关访问 Jev **作者：** Claude Code

## 背景

讨论过一个方向：路由不再让规则先判，只用 Jev 判断，重点放在构建发给 Jev 的上下文上。没有数据之前不改线上路由，先做两样东西：

- `routing.Jev.Rich`：丰富的 state 和 criteria（`routing/jevstate.go`）。
- `routing.Router.JevFirst`：先问 Jev，Jev 用不了（超时、失败、不在候选、把握不足）再走规则 → 记忆 → 默认。

两者在 app 里都没有打开，只有 `cmd/routebench` 用它们。

## 丰富的 state 比现在多了什么

| 项 | 现在（基础） | 丰富 |
|---|---|---|
| 选中文本 | 超过 1200 字截头尾 | 同左，用 `<<< >>>` 包住 |
| 前后文 | 不发 | 同一输入框或页面里，选区前后各最多 200 字，用 `[SELECTION]` 标出选区位置 |
| 应用 | bundle id | 常见应用的名字和类型，例如“Claude (a chat with an AI assistant)”，再附上 bundle id |
| 可编辑 | yes/no/unknown | 用一句话说明含义（在输入框里写 / 在读的内容） |
| 语言 | 只说文字类别 | 直接说选区是不是用户的语言 |
| 形状 | 字数、行数、类别、结构 | 再加 Agent 汇报特征数、像请求的短语数、是否以问号结尾 |
| 规则 | 不发 | 每个候选功能的规则分数，注明“只是提示，歧义时常错” |
| 偏好 | 中文摘要 | 英文，同样的内容：三个范围的占比和样本数、最近选择、改正 |
| criteria | `Name：Purpose` | 内置功能再加一段“什么时候选、什么时候不选”（`guides`） |

窗口标题仍然只在用户允许时才发。`go run ./cmd/routebench -show c1` 可以打印某条样例的两种 state，不发请求。

**隐私差异：** 丰富 state 会把选区前后的文字发给 TypeSafe。这些前后文现在已经作为 `Surrounding` 发给功能的模型服务，但那是用户自己配的服务，Jev 是另一家。要不要打开，需要负责人决定。

## 样例

在原有 35 条之外，新加 5 条带前后文的样例（c1–c5）：同一个英文词分别出现在中文聊天或中文技术文章里，和出现在英文文章里。前者期望“释义”，后者期望“翻译”。这只是样例作者的假设：中文读者遇到夹在中文里的英文词，想要的是意思，不是译文。规则看不到前后文，`TestSamples` 不把这 5 条算进规则的判对或判错，只打印出来。

## 结果（已实测，2026-11-08，每条样例每种方式调用 1 次）

| | 明确样例 34 条判对 | 其中带前后文 5 条 | 平均把握 | state 平均字数 | 延迟 p50 / p95 / 最大 |
|---|---|---|---|---|---|
| 规则 | 31（只算规则自己判定的） | 2 | — | — | 约 11µs |
| Jev（现在的 state） | 30 | 4 | 0.71 | 326 | 298ms / 815ms / 1.42s |
| Jev + 丰富上下文 | 33 | 5 | 0.87 | 772 | 295ms / 333ms / 337ms |

逐条要点：

- **Agent 输出：** 现在的 Jev 把 a1、a4、a6 判成翻译。a1 是一段带 Markdown 的 Claude 汇报，判错很意外。丰富上下文修好了 a1 和 a6，a4（VS Code 里没有结构的一段汇报）仍判为翻译，把握 0.41。
- **前后文样例：** 现在的 Jev 看不到前后文，c1–c4 却也选了释义，但把握只有 0.35–0.56。按现在 0.6 的阈值，线上都会被丢弃。c5 选了释义，判错。丰富上下文 5 条全对，把握 0.51–0.72，其中 c4（0.51）仍低于阈值。
- **把握整体变高：** 丰富上下文在明确样例上大多 0.9 以上。`confidence` 没有校准过，变高不等于更可能判对。
- **歧义样例：** 丰富上下文 6 条里 5 条选了翻译。t8、t10（只读环境里的英文俚语）现在的 Jev 选的是释义，丰富上下文选了翻译。当时怀疑是规则分数带来的锚定，下一节的对比否定了这个猜测。
- **延迟：** 两种方式的 p50 都在 300ms 左右，state 变长没有让延迟变长。现在的 Jev 那 1.42s 和 815ms 是单次的离群值，原因没查（可能是连接预热，推测）。只有 40 次，p95 不可靠。

## 去掉规则提示（已实测，2026-11-08，同样的设置跑了两轮）

加了 `Jev.NoHints`：丰富 state 里不放规则分数，其余不变。

| | 明确样例 34 条判对（第 1 轮 / 第 2 轮） | 带前后文 5 条 | 平均把握 | state 平均字数 | 延迟 p50 |
|---|---|---|---|---|---|
| 规则 | 31 / 31 | 2 / 2 | — | — | 约 11µs |
| Jev（现在的 state） | 28 / 28 | 2 / 3 | 0.71 / 0.72 | 326 | 约 308ms |
| Jev + 丰富上下文 | 33 / 33 | 5 / 5 | 0.87 / 0.86 | 772 | 约 310ms |
| 丰富上下文、不带规则提示 | 31 / 31 | 5 / 5 | 0.85 / 0.86 | 623 | 约 305ms |

- **锚定的猜测不成立。** 不带规则提示时，t8、t10 仍然选翻译，所以是前后文缺失加上 guides 的写法导致的，不是规则分数导致的。这两条没有前后文，guides 写的是“读的外文选翻译”，这个选择符合 guides，对不对要看负责人的标注。
- **规则提示救的是 Agent 汇报。** 去掉提示后，英文的 Agent 汇报 a1、a6 又判成了翻译，a4 一直判错。而且这几条的把握是 0.67–0.79，高于 0.6 的阈值，打开 `JevFirst` 时线上会真的选错，不会回退到规则。Jev 自己倾向于把英文的 Agent 汇报看成“要翻译的外文”，规则抽出的特征正好补上这一点。
- **前后文的效果和提示无关。** c1–c5 在两种丰富 state 下都 5/5。
- **现在的 state 不太稳定。** 同样的样例，第一次测 30 条，这两轮都是 28 条，几条低把握的结果在两个选项之间来回变。丰富上下文两轮都是 33 条，逐条结果几乎一样。
- **低把握的问题仍在。** 丰富上下文、带提示时，a6、c3、c4 的把握在 0.39–0.53 之间，打开 `JevFirst` 后会回退到规则。其中 c3、c4 的规则会判成翻译，是错的。所以阈值也要一起重新定。

结论（只基于这批自写样例）：**规则不该删，应该改成给 Jev 的特征。** 只用 Jev、不给规则信号时，在 Agent 汇报上比规则差，而且错的时候把握还很高。

## 不能下的结论

- 样例是开发时写的，规则就是在这些样例上调出来的，guides 也是看着这些样例写的。丰富上下文判对 33 条有过拟合的成分。
- 每种方式只跑了两轮，每轮每条调用 1 次。
- 网络环境是本地网关，换环境后延迟可能不同。
- 规则提示的作用测了；前后文和 guides 各自的贡献还没有分开测。
